# Security model

@mcpapps's real security boundary is **the host's sandboxed iframe**, not this framework's
code. The framework assumes: the host renders the component in a locked-down cross-origin
(or opaque-origin `srcdoc`) iframe, the host enforces the CSP the component declares, and
the only window able to `postMessage` the component is the host. Those assumptions hold on
Claude and ChatGPT — but they're properties of the *deployment environment*, not the code,
so it's worth being explicit about where the line sits.

## The postMessage boundary

`@mcpapps/client-core`'s default transport posts to `window.parent` with `targetOrigin: "*"`
and, by default, accepts any inbound message whose `event.source` is that same window
(any origin). The wildcard `targetOrigin` and the lack of a default `expectedOrigin` are
deliberate: a sandboxed `srcdoc` iframe has an **opaque** (`"null"`) origin, so pinning a
specific origin by default would break the most common deployment (Claude/ChatGPT serving
an inlined, `srcdoc`-loaded component).

If your deployment gives the component a concrete, known host origin (e.g. a `basePath`
component served same-origin, or a dedicated sandbox `domain`), harden the bridge:

```ts
import { createHostBridge } from "@mcpapps/client-core";

const bridge = createHostBridge({ expectedOrigin: "https://your-known-host.example.com" });
```

`event.source` identity (not origin) is always checked — only a message actually posted by
the window the bridge would send to is ever considered, regardless of `expectedOrigin`.

Inbound host notifications (`tool-input`, `host-context-changed`) are also shape-checked
before they're trusted: a malformed payload is dropped rather than applied, without pulling
in a schema-validation library (bundle size matters in the iframe).

## CSP is declarative, not enforced by the server

`_meta.ui.csp` is a **declaration** the component makes; the MCP server never sets a
`Content-Security-Policy` HTTP header itself. Enforcement is entirely the host's
responsibility — it reads the declared `connectDomains`/`resourceDomains`/`frameDomains`/
`baseUriDomains` and builds the sandbox's actual CSP from them. A host that ignores the
declaration gives the component no CSP at all; `mcpapps audit` validates the *shape and
syntax* of what you declare (see [host profiles](/concepts/host-profiles)), not that a given
host enforces it.

## The MCP server itself

`createMcpHandler` ships permissive-by-default CORS (`Access-Control-Allow-Origin: *`) and
no authentication, because the shipped example tools are deterministic with no side effects
or secrets. A real deployment with side-effecting tools or credentials should supply both:

```ts
createMcpHandler(app, {
  cors: { origin: "https://your-trusted-origin.example.com" },
  authorize: (request) => request.headers.get("Authorization") === `Bearer ${expected}`,
});
```

`authorize` runs after CORS preflight (which must always succeed) and before any body
parsing — a rejection short-circuits with a `401` before the request reaches tool dispatch.

## What's already handled for you

- Tool **input and output** are validated against their `zod` schemas on the server before
  a result ever reaches the host.
- Inlined build output (Flutter's single-HTML fold, Vue's compiled bundle) is guarded
  against a literal `</script>`/`</style>` breaking out of its wrapping tag.
- Flutter assets are base64-encoded before being embedded, so asset *bytes* can't smuggle a
  tag breakout — only build-output *filenames* need the guard above.

::note
None of this replaces reading the [host profiles](/concepts/host-profiles) page if you're
targeting a specific host's guarantees — CSP enforcement, single-file delivery, and
byte-size limits vary by host, and are called out there per host, not here.
::
